# Baize Agent V25 计划 · 专家评审（P2–P5）

- **评审日期**：2026-08-19
- **评审人**：Agent 工程师（吴八哥视角）、软件架构师（架构通视角）、AI 工程师（深网网视角）三线并行评审 + 计划原文交叉核对
- **评审范围**：`docs/baize-agent-V25升级计划.md` 的 P2（MCP 兼容）、P3（模型供应商）、P4（向量/RAG）、P5（多智能体编排）
- **评审约束（项目独特性，全程不得破坏）**：运行时零第三方依赖（核心 `baize/` 纯 stdlib）、NO FAKE DONE + manifest 证据 + doctor/gate/pytest 门禁（基线 422 passed / 1 skipped / 0 failed）、plugin/component 插件化、autonomy、组合内核、Verifier、`baize serve` 内建 HTTP。

---

## 0. 三线共识（最重要的结论）

**计划的核心方向对，但 P2–P5 严重低估了「主干已经有什么」**——三位专家独立读源码后一致指出：

| 阶段 | 计划假设 | 源码实际 | 结论 |
|------|----------|----------|------|
| P2 MCP | 全新接入层 | 全新（确实缺） | ✅ 真缺口，保留 |
| P3 供应商 | 新建 providers | `llm.py` 已有 openai/anthropic/ollama 适配器 + `BAIZE_MODEL_ROUTER` | ⚠️ 大半已存在，勿搬核心 |
| P4 向量 | 新建 VectorBackend | `vector.py` 已有 `get_backend()` + `TfidfIndex` + `EmbeddingBackend`；`rag.py` 直连 `TfidfIndex` | ⚠️ 双实现腐烂风险 |
| P5 多智能体 | 新建 Role/Crew | `orchestrator.py` 已有 Director→Executor→Verifier + `TeamMemory`；`baize team` 已存在 | ⚠️ 勿重写，做薄配置层 |

**统一收口（架构师核心意见）**：计划漏了既有 `plugin.py`/`component.py` 扩展总线。若 P2–P5 各自 `import baize.ext.X`，会把扩展机制碎成三条平行山头。V25 必须做的一处基础设施改动 = 把生态接入统一收口到 `plugin.discover` + `CompositionKernel.add_component`，而非各阶段自起炉灶。

**优先级收敛**：**P2 > P5 > P3(降级为补丁) > P4(可推迟 V26)**。重后端（llama_index / chromadb / gemini / bedrock）建议推迟到 V26，避免 `ext/` 膨胀与测试 skip 面扩大，守住零依赖/可验证独特性。

## P2 · MCP 兼容 — approve-with-changes

**价值**：三位一致认为这是 V25 ROI 最高的一项（最小代价接最大工具生态），且纯 `subprocess`+管道，**不威胁零依赖**。

**风险与修正**
1. **协议正确性（Agent 工程师 / AI 工程师）**：MCP 是带 `Content-Length:` 头部的 JSON-RPC 2.0 分帧，**不是纯换行 JSON**。`initialize` 需 `protocolVersion` 协商 + `capabilities` 交换，且初始化后必须发 `notifications/initialized`，否则多数真实 server（Claude Desktop/Cursor）静默挂起。计划里「管道 + JSON-RPC」易漏分帧与握手。
   - 修正：`baize/ext/mcp/transport.py` 严格实现 Content-Length 分帧与 initialize 握手；只用 mock 测试不够，**必须对真实参考 server 联调**。
2. **集成点错位（Agent 工程师）**：`tools.py` 的 `register_mcp_client(spec)` 应把 MCP 工具包装进**现有 `ToolRegistry`**（复用 `tools.py` 的 `register/execute`），使 MCP 工具自动进入 LLM schema——而不是绕过既有内核另立工具表。
3. **门禁写法是假绿（架构师）**：「`import baize` 后断言 `baize.ext` 未被自动导入」恒真（`__init__.py` 只设 `__version__`，永不 import ext）。真不变量应是**静态 grep**：`baize/*.py` 无顶层 `import baize.ext`。建议把此 grep 做成门禁脚本，而非运行时断言。

## P3 · 模型供应商 — approve-with-changes（建议降级为补丁）

**风险与修正**
1. **勿搬核心适配器（架构师 / Agent 工程师 / AI 工程师 三方一致）**：`llm.py:102–201` 已内建 anthropic/ollama 适配器（纯 stdlib），`BAIZE_MODEL_ROUTER` 已在核心解析。把 `openai.py`「迁 ext 并保留默认」与「核心仅解析 router 时延迟导入、默认路径纯 stdlib」**自相矛盾**——若默认客户端真迁 ext，默认路径即触碰 ext，**破零依赖红线**。
   - 修正：既有 stdlib 适配器**留在 `llm.py` 不动**；`baize/ext/providers/` 只放**真正非 OpenAI 兼容**的厂商（gemini / bedrock 等薄适配）；`llm.py` 仅在 `_route_from_config` 内延迟 import ext，仅当命名 provider 非内建才懒查 ext registry。无循环依赖。
2. **补真实能力缺口（AI 工程师）**，而非凑供应商数量：
   - Anthropic 流式未实装，降级为单次 yield，且 `max_tokens` 硬编码 4096 易截断长输出；
   - DeepSeek reasoner 的 `reasoning_content` 未捕获；
   - `provider_capabilities` 恒返 `stream/tools=True`，能力路由形同虚设 → **这是 NO FAKE DONE 视角的假绿**，应如实报 `{"stream": False, "tools": True}`。
3. **P3 应从计划降级为「补丁 + 非兼容厂商薄适配」**，不新建完整 providers 模块。

## P4 · 向量 / RAG — approve-with-changes（建议可推迟 V26）

**风险与修正**
1. **双实现腐烂（架构师 / Agent 工程师 一致）**：`vector.py:133` 已有 `get_backend()` + `TfidfIndex` + `EmbeddingBackend` 后端工厂。P4 另起 `VectorBackend(add/query)` + `tfidf_backend` 包装 = 两层平行抽象，且 `rag.py:23` 直接 `from .vector import TfidfIndex` 不走工厂，换后端对 RAG 无效。
   - 修正：扩展既有 `get_backend()` 让其懒探测 `ext/vector_backends`，**勿新造接口**；`rag.py` 改走 `get_backend()`。
2. **稠密后端被低估（AI 工程师）**：`EmbeddingBackend` 只有 `embed()`，无向量索引/ANN；P4 的 `add/query` 稠密后端需自建索引层（或接 chromadb），工作量被计划低估。默认 TF-IDF 是**真**词法检索（非假 RAG），但语义/同义/跨语种弱——README 勿吹成语义检索，诚实标 lexical retrieval。**不威胁零依赖**（稠密后端放 ext）。
3. **测试崩溃风险（架构师）**：llama_index/chromadb 后端测试用 `pytest.importorskip` 守卫；否则缺依赖时**整批收集即崩**（非 skip），会直接威胁 422/1 skip 基线。

## P5 · 多智能体编排 — approve-with-changes

**价值**：建立在已有 `orchestrator.py`（Director→Executor→Verifier + 确定性门 `run_checks` + 重试 + `verify_hooks`）之上，成本低、能真正提升能力。

**风险与修正**
1. **概念错位（架构师 / Agent 工程师 一致）**：「复用 `component.Kind` 作为角色单元」是**错误**——`Kind` 是封闭枚举（MODEL/TOOL/…）的粗粒度组件类，而 Role（coder/reviewer）是 prompt + 工具集的 agent 实例，混用会污染契约。
2. **勿重写（AI 工程师）**：`baize team` 已存在，`orchestrator.py` 已含 TeamMemory 黑板交接 + LLM verifier（默认 fail-closed）。新 `Role/Crew` 若另起炉灶即成壳。
   - 修正：新增 `baize/team.py` 只做**薄配置层**，把 `roles.yaml`（role→system_prompt+tools）映射为对现有 `Orchestrator` 的 `Agent(role=...)` 调用，复用 `Verifier` + `TeamMemory`；挂在现有 `team` 子命令下（`--roles`），角色缺失 fail-closed 报错。

## 跨阶段红线修正（影响 P2–P5 全部）

1. **统一扩展总线**：P2–P5 全部经 `plugin.discover` + `CompositionKernel.add_component` 注册，禁止各阶段自起 `import baize.ext.X` 平行机制。
2. **门禁去假绿**：把「核心不依赖 ext」改成**静态 grep 门禁**（核心 `baize/*.py` 无顶层 `import baize.ext`）；`provider_capabilities` 如实上报。
3. **守住 422 基线**：`pyproject.toml` 的 `norecursedirs` **补 `ext`**；`ext` 相关测试放进 `tests/` 时必须用 `importorskip` 守卫，否则缺依赖会整批 collection 崩溃，威胁 422 passed / 1 skipped 基线。
4. **零依赖默认路径**：任何默认启用的能力（如默认 LLM 客户端）不得触碰 `ext/`；`ext` 仅在不改变默认行为的前提下按需懒加载。

---

## 修订后的 V25 范围建议

- **必做（进 V25）**：P0 元数据、P1 README 修正、P2 MCP（修正分帧+握手+接入 ToolRegistry+静态 grep 门禁）、P5 多智能体（薄配置层复用 orchestrator）。
- **降级做（进 V25，但缩范围）**：P3 改为「补核心适配器缺口（Anthropic 流式/max_tokens/DeepSeek reasoning + 如实 capabilities）+ 仅加非 OpenAI 兼容厂商薄适配」，不搬核心代码。
- **推迟（V26）**：P4 稠密向量后端（llama_index/chromadb）、P3 的 gemini/bedrock 等重后端、`ext/` 大规模生态扩张。
- **P6/P7**：随上述范围调整，COMPARISON 与 examples 聚焦 MCP + team。

> 评审结论：计划方向正确，但需在「尊重主干既有能力」前提下收缩重做面、统一扩展总线、修正门禁假绿。落地优先级 **P2 > P5 > P3(补丁) > P4(推迟)**。
