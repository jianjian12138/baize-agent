# 10 · 从使用者到贡献者

> 目标：让你提交的 PR 能被合并，而不是在门禁上撞墙。
> 本篇会解释三条项目原则、一个必跑清单，以及"为什么门禁是红的还能继续开发"。

---

## 1. 三条原则（请务必尊重）

### 1.1 运行时只用标准库

> `baize/` 包必须保持**纯 Python 标准库**，**不得引入任何第三方运行时依赖**。

需要系统接口的新能力（MCP、OS 沙箱、钩子）应该放在**默认关闭的可选适配层**里，绝不能污染白盒核心。

**为什么这么严？** 因为"零依赖"是这个项目最重要的信任基础之一：

- 审计面小到可以通读；
- 不会因为某个依赖被投毒而沦陷；
- `import baize` 在任何环境都能成功。

如果确实需要可选依赖，用这三种**被允许**的写法：

```python
# 写法 1：try/except ImportError
try:
    import webview
except ImportError:
    webview = None

# 写法 2：函数体内 import（延迟到真正用到时才加载）
def _apply_landlock(workspace):
    import landlock
    ...

# 写法 3：TYPE_CHECKING（只给类型检查器看）
if TYPE_CHECKING:
    import coverage
```

这三种都会被零依赖门禁识别为 **SOFT**，列出来但不判失败。

### 1.2 NO FAKE DONE

> 每一个"完成了"都必须有**物理证据**和**独立验证**。不要报告你无法证明的成功。拿不准的时候，**失败要关（fail closed）**。

具体到代码里：

| 场景 | 错误做法 | 白泽的做法 |
| :--- | :--- | :--- |
| 命令执行失败 | 返回 `returncode: 0` | 返回真实退出码 |
| 沙箱不可用 | 假装有沙箱 | `degraded=True` + 明确警告 |
| 覆盖率不够 | 调低下限 | 让门禁红着，并公开记录 |
| 模型没配 | 发一个注定失败的请求 | 拒绝启动，提示怎么配 |
| 环境做不到 | 跳过但不说明 | 跳过并打印**具体原因** |

**第 5 条值得展开**：这个仓库里确实有 2 个测试是**跳过**的。它们不是被忽略的失败，而是**环境能力不足**。跳过的理由是：

> PowerShell in this environment cannot launch absolute-path executables (starts, exits 0, empty stdout); the test needs PowerShell to run `python`. Not a product defect.

这个判断是**有对照实验支撑的**：

| PowerShell 命令 | 结果 |
| :--- | :--- |
| `echo BAIZE_PS_PROBE`（内建命令） | `BAIZE_PS_PROBE` ✅ |
| `& "C:\Windows\System32\cmd.exe" /c echo BAIZE_PS_PROBE`（绝对路径程序） | 空输出，退出码 0 ❌ |
| `& "<绝对路径>\python.exe" -c "print(1)"` | 空输出，退出码 0 ❌ |

内建命令能返回输出、任何绝对路径程序都静默失败 —— 这说明**失败不在被测代码里**，所以跳过而不是伪造通过。

### 1.3 诚实优先于功能

> 我们宁愿做一个值得信赖的基础，也不愿做一个功能对齐商业 Agent 的克隆。优先选择深度和可证明性。

这条决定了项目的气质：**它不追求功能清单更长，它追求每个承诺都经得起检验。**

## 2. 开发环境

运行时只需要 Python ≥ 3.10（在 3.13 上测试过）。核心不需要安装步骤。

```bash
python -m venv .venv

# Windows
.venv/Scripts/pip install pytest
.venv/Scripts/python -m pytest tests/ -q

# macOS / Linux
.venv/bin/pip install pytest
.venv/bin/python -m pytest tests/ -q
```

或者直接：

```bash
make test
```

## 3. 提 PR 前的清单

- [ ] `python -m baize.cli doctor` 通过（真实环境门禁）
- [ ] `pytest tests/` 全绿
- [ ] `make truth` 通过（版本/测试数无漂移）
- [ ] `make hygiene` 通过（没有垃圾文件被提交）
- [ ] `make deps` 通过（零依赖契约没被破坏）
- [ ] 覆盖率不低于 `config.TEST_COVERAGE_THRESHOLD`（**当前这一项是红的，见第 5 节**）
- [ ] 新工具是**注册了 JSON schema 的原语**，不要把功能塞进核心循环
- [ ] 改动小而可审查，PR 里说明**为什么**这么改

一条命令跑完前四项：

```bash
make gate
```

## 4. 永远不要手打版本号和测试数

`baize/__init__.py` 里有**全仓库唯一的**版本字面量：

```python
__version__  = "37.0.0"
__codename__ = "Prometheus"
```

其他所有出现位置——README 标题、shields.io 徽章、对比表表头、`AGENT.md`、QUICKSTART/USAGE_GUIDE、`baize.manifest.json`、`pyproject.toml`——**全部**由 `scripts/sync_truth.py` 从这两行派生。

测试徽章同样是**实测出来的**（跑一遍测试套件），不是手写的。

### 4.1 发版本的正确姿势

```bash
# 1. 改 baize/__init__.py 里的两行
# 2. 重新生成所有派生位置
python scripts/sync_truth.py

# 3. 验证没有漂移
make truth
```

### 4.2 为什么这么严

因为这个仓库**真的犯过这个错**：

- README 曾经整整一个版本都在宣传 `V36.0.0 Titan`；
- 测试徽章曾经写着 `53/53`，而套件里其实有 650 个用例；
- `.env.example` 写着 V25.0.0，两个安装脚本写着 V33.0.0，而实际版本是 V37.0.0；
- 系统提示里对模型说"你是 V33 runtime"，实际是 V37——**每个模型调用都被告知了错误的版本**。

最后一类问题最隐蔽：它不是文档错误，而是**运行时行为错误**。修复方式不是改字符串，而是**让它读单一真相源**：

```python
from . import __version__
...
f"You are Baize, an autonomous engineering agent (V{__version__} runtime). "
```

**从"记得改"变成"不可能不改"** —— 这是解决这类问题的唯一可靠办法。

### 4.3 哪些不能动

历史版本引用是**受保护**的，永远不会被重写。比如 README 分支表里的：

```
V26.0.0「闭环事实内核」架构重构线
V33.0.0 升级线
```

这些是**历史事实**，不是当前版本。`sync_truth.py` 里有 `PROTECTED_LITERALS` 明确列出它们——防止一次粗暴的全量替换把历史抹掉。

## 5. 门禁红了或绿了，都不许改数字

门禁的输出只说明一件事：**它测到了什么**。覆盖率不够它报红，够了它报绿；两种情况它都会打印自己读的是哪个数据文件、那个文件是什么时候写的。

**曾经的状态**：覆盖率 77.4% < 85%，门禁 RED。这个缺口当时被公开记录在三处：

| 位置 | 当时写的内容 |
| :--- | :--- |
| `baize/config.py` | `KNOWN GAP (measured 2026-09-17 on v30-dev): actual coverage is 77.4%` |
| `CONTRIBUTING.md` | `**This gate is currently RED** - measured coverage is 77.4%` |
| `.env.example` | `Measured coverage on 2026-09-17 was 77.4%, so the gate fails` |

后来查清了根因：那个 77.4% 是在一棵**不完整的树**上测出来的——24 个文件（2 个源码、3 个门禁脚本、17 个测试文件）一直没被提交。把它们提交之后，覆盖率是 86.6%，门禁转绿。

**这件事本身是本篇最值钱的教训**：上面三处文字里的百分比，在写下它的当天就开始过期，而它们仍然用**现在时**向每个读者宣布"门禁是红的"。所以这三处现在都不再写具体数字，只写契约（下限 85）和"当前值用 `make cov` 看"。数字写在散文里，就是一次测量穿上了承诺的外衣。

### 5.1 为什么不让它变绿

因为让它变绿有两条路：

| 做法 | 结果 |
| :--- | :--- |
| ❌ 把 `TEST_COVERAGE_THRESHOLD` 改成 75 | 门禁绿了，**但你骗了自己** |
| ✅ 补测试到 85% | 门禁绿了，**而且是真的** |

这个项目选了第三条路：**红着，并且告诉你为什么红。**

`tests/test_config.py` 里有一条测试专门钉住这个值：

```python
assert cfg["TEST_COVERAGE_THRESHOLD"] == "85"
```

**它就是用来阻止"改小目标"这种操作的。** 如果你改了那个数字，测试会失败并告诉你：你改的是契约，不是测试过期了。

### 5.2 你能怎么帮

补测试。`make cov` 会打印每个文件的缺失行号：

```
baize\cli.py    741  269  236  21  62%  32-33, 72->74, 81-142, ...
baize\ui.py     112   12   34   6  86%  32, 34, 37-44, ...
```

挑一个缺口补上，就是最有价值的贡献。

> 顺便说：`baize/docker_sandbox.py` 曾经只有 71% 覆盖——**整个 Docker 容器路径（第 104-140 行）一行都没被执行过**，因为没有 Docker 守护进程就进不去那个分支。后来用**桩住 subprocess 边界**的方式补上了测试，现在是 **100%**。
>
> 教训：**"这段代码在这个环境跑不到"不等于"这段代码不用测"。** 桩住边界就能测。

## 6. `.gitignore` 不会取消跟踪任何东西

这是新手最容易犯的错误：

> `.gitignore` **只影响未跟踪的文件**。把一个路径加进去，**不会**把它从索引里移除。

这个仓库因此吃过亏：78 个 `__pycache__` 字节码、31 个 `persistence/` 运行时文件、21 个探针脚本**被提交进仓库好几个月**——而 `.gitignore` 里明明列着这些路径。

要删掉已经跟踪的东西，**保留磁盘文件、从索引移除**：

```bash
git rm -r --cached <path>     # 你还想在本地留着的运行时状态
git rm <path>                 # 对别人毫无价值的一次性脚本
```

`make hygiene` 会扫描索引里的垃圾并在 CI 里报错。

### 6.1 反过来说：被忽略的目录也可能需要存在

`projects/` 曾被整个忽略：

```
projects/
```

但 `doctor` 要求这个目录**必须存在**（`required=True`），而没有任何代码会创建它。

**结果：每一个新克隆的仓库，`doctor` 都必然失败** —— 文档里宣传的"1 分钟极速上手"永远走不通。

修复方式是"**目录进仓库，内容不进**"：

```
projects/*
!projects/.gitkeep
```

**这类"文档说的和代码做的不一致"的问题，是最值得优先修的**——因为它影响的是每一个新用户的前五分钟。

## 7. 报告问题

提 issue 时请包含：

1. **环境**（操作系统、Python 版本）；
2. **执行的命令**（原样复制）；
3. **观察到的行为 vs 期望的行为**；
4. 相关的 **`Baize Doctor Report` 输出**。

如果是一个门禁失败，请把**完整的门禁输出**贴上来——那些输出里的每个数字都是可追溯的，能大幅缩短排查时间。

## 8. 一个真实贡献的完整流程（案例）

下面是一次真实修复的全过程，可以作为模板：

**① 发现**：跑 `baize run` 时日志里出现一行 warning：

```
[harvester] failed to rebuild index: module 'baize.skill_index' has no attribute 'build'
```

**② 定位**：`skill_harvester.py:147` 调用 `skill_index.build()`，但模块暴露的是 `build_index()`。

**③ 评估影响**：这个异常被 `except Exception` 吞成一行 warning，所以**每个被蒸馏出的技能都写到了磁盘上、却永远进不了索引**——学习闭环等于白学。

**④ 修复**：改成正确的函数名。

**⑤ 加测试（关键）**：不能只测"函数被调用了"，要测**真正的契约**：

```python
def test_harvester_calls_an_existing_skill_index_attribute(self):
    """Any skill_index.<attr> referenced in the harvester must exist."""
    tree = ast.parse(src)
    referenced = {n.attr for n in ast.walk(tree)
                  if isinstance(n, ast.Attribute)
                  and isinstance(n.value, ast.Name)
                  and n.value.id == "skill_index"}
    missing = sorted(n for n in referenced if not hasattr(skill_index, n))
    self.assertEqual(missing, [])
```

**用 AST 而不是正则**——因为正则会把注释里的 `skill_index.py` 也匹配上，报出一个假的 `py` 属性。

**⑥ 证伪**：把修复回退，确认测试**真的会失败**：

```
AssertionError: Lists differ: ['build'] != []
```

**⑦ 端到端验证**：真跑一次 `baize run`，确认 warning 消失，且蒸馏出的技能**出现在索引里**：

```
 -> auto-创建一个-hello-baizetxt-文件内容为-hello-from-bai | user:user_skills
```

**这个流程里每一步都不能省**，尤其是 ⑥ 和 ⑦：

- 没有 ⑥，你不知道测试是不是永远绿的（那样它就没有价值）；
- 没有 ⑦，你不知道修复在真实运行里是否生效。

## 本篇小结

- 三条原则：**只用标准库**、**NO FAKE DONE**、**诚实优先于功能**。
- 可选依赖有**三种被允许的写法**（try/except、函数体内、TYPE_CHECKING），它们被识别为 SOFT。
- 提 PR 前跑 `make gate`；覆盖率那一项**当前是红的，这是已知缺口**。
- **永远不要手打版本号和测试数**——`baize/__init__.py` 是唯一真相源，`make truth` 会抓漂移。
- 能读单一真相源的地方就让它读（比如系统提示的版本号），**从"记得改"变成"不可能不改"**。
- `.gitignore` **不会**取消跟踪；用 `git rm --cached`。
- 被忽略的目录也可能需要存在——`projects/` 就是这么坑了新用户的第一次 `doctor`。
- 加测试之后要**证伪**（回退修复，确认测试会红），并**端到端验证**。
