# 09 · 部署到生产

> 目标：把白泽装进容器、接进 CI、接进监控。
> 本篇会详细解释 Dockerfile 里的**每一个细节为什么这么写**——因为里面有几个坑，踩了会静默失效。

---

## 1. Dockerfile 逐行解读

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.11-slim

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    git \
    curl \
    && rm -rf /var/lib/apt/lists/*

COPY pyproject.toml .
COPY baize/ ./baize/
COPY assets/ ./assets/

RUN pip install --no-cache-dir -e .

RUN mkdir -p /app/persistence /app/projects

ENV BAIZE_SERVE_HOST=0.0.0.0
ENV BAIZE_SERVE_PORT=8787

EXPOSE 8787 50051

HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
    CMD python -c "import os,sys,urllib.request; \
port=os.environ.get('BAIZE_SERVE_PORT','8787'); \
sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:'+port+'/health', timeout=4).status==200 else 1)"

CMD ["python", "-m", "baize", "serve", "--port", "8787"]
```

### 1.1 为什么 `COPY assets/` 是必需的

`assets/` 是技能库。`BAIZE_ASSETS_DIR` 默认指向 `<root>/assets`，`baize index build` 会扫描它。

**漏掉这一行的后果**：容器起来了，但技能索引是空的——Agent 一个技能都不会用，而且**不会报错**。

这是最阴险的一类 bug：**功能静默降级，看起来一切正常。**

（`assets/` 是 1.9 MB / 59 个文件，`.dockerignore` 没有排除它，所以 `COPY` 能正常解析。）

### 1.2 为什么不能 `COPY docs/`

`COPY` 的源路径是**相对于过滤后的构建上下文**解析的（`.dockerignore` 已经生效）。如果 `docs/` 被 `.dockerignore` 排除了，那么：

```dockerfile
COPY docs/ ./docs/      # ❌
```

构建会直接失败：

```
failed to compute cache key: "/docs": not found
```

**注意这个错误信息的误导性**：它说 "not found"，你会以为是路径写错了，其实是**被 `.dockerignore` 过滤掉了**。而且运行时根本没人读 `docs/`——所以这一行既没用又让镜像构建不了。

### 1.3 为什么必须 `mkdir -p /app/projects`

`baize/doctor.py` 把这两个目录标记为**必需**：

```python
for key in ("BAIZE_PERSISTENCE_DIR", "BAIZE_PROJECTS_DIR", "BAIZE_ASSETS_DIR"):
    p = Path(cfg[key])
    report.add(f"dir {key}", p.is_dir(), required=True, detail=str(p))
```

所以镜像里必须先建好，否则：

```bash
docker run --rm baize:ci doctor    # ❌ RESULT: FAILED
```

CI 的 `docker` 作业里就有这一步（`docker run --rm baize:ci doctor`），这也是它当时一直在报错的原因。

### 1.4 ⚠️ 最阴险的坑：ENV 名字写错会静默失效

旧 Dockerfile 里是：

```dockerfile
ENV BAIZE_HOST=0.0.0.0      # ❌ 没有任何代码读这个键
ENV BAIZE_PORT=8787         # ❌ 没有任何代码读这个键
```

但 `baize/serve.py` 真正读的是：

```bash
BAIZE_SERVE_HOST
BAIZE_SERVE_PORT
```

**后果链条：**

1. 这两行 ENV **完全无效**（不存在的键，Docker 不会报错）；
2. 服务按默认值监听 `127.0.0.1`；
3. 容器内 `127.0.0.1` 是**容器自己**，不是宿主机；
4. `docker run -p 8787:8787` **打不通**；
5. 而且没有任何报错——端口映射看起来成功了，服务看起来启动了，就是连不上。

**这是一个"三处都看起来对、就是不通"的经典故障。**

> **怎么防这类问题？** 有一条测试专门检查这个（`tests/test_dockerfile_context.py`）：
> ```python
> def test_every_baize_env_key_is_a_real_config_key():
>     from baize.config import _DEFAULTS
>     unknown = [n for n in names if n not in _DEFAULTS]
> ```
> 它把 Dockerfile 里所有 `ENV BAIZE_*` 的名字和真实的配置键表对比，**任何一个不存在的键都会让测试失败**。
>
> 而且这条测试是**证明过有效的**：拿修复前的 Dockerfile 跑，6 条里有 4 条失败。

### 1.5 HEALTHCHECK 为什么不用 curl

```dockerfile
CMD python -c "import os,sys,urllib.request; ..."
```

因为**零依赖**：`urllib.request` 是标准库，不需要在镜像里装 `curl`（虽然上面 apt 装了 curl 是给别的地方用的）。

`--start-period=15s` 给服务启动留出时间，避免刚起来就被判定为不健康。

`/health` 返回：

```json
{"status": "ok", "version": "37.0.0"}
```

## 2. 构建与运行

```bash
docker build -t baize:ci .
docker run --rm baize:ci --version
docker run --rm baize:ci doctor
docker run -p 8787:8787 baize:ci
```

验证：

```bash
curl http://localhost:8787/health
# {"status": "ok", "version": "37.0.0"}
```

### 2.1 如果连不上

按这个顺序查：

1. **容器里服务真的在监听吗？**
   ```bash
   docker exec <container> python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8787/health').read())"
   ```
   如果容器内通、宿主机不通 → **`BAIZE_SERVE_HOST` 没设成 `0.0.0.0`**（见 1.4）。

2. **镜像里技能库有没有？**
   ```bash
   docker run --rm baize:ci python -m baize index build
   # 应该输出 indexed 23 skills from 1 source(s)
   ```
   如果是 0 个 → **`COPY assets/` 漏了**（见 1.1）。

## 3. CI 的四类作业

`.github/workflows/ci.yml` 定义了四个作业：

### 3.1 `test` —— 12 个并行组合

```yaml
matrix:
  os: [ubuntu-latest, windows-latest, macos-latest]
  python: ["3.10", "3.11", "3.12", "3.13"]
```

**3 系统 × 4 Python 版本 = 12 个作业**，`fail-fast: false`（一个挂了其他继续跑完，方便一次性看到所有问题）。

每个作业跑：

| 步骤 | 命令 | 作用 |
| :--- | :--- | :--- |
| 安装测试工具 | `pip install pytest pytest-cov` | 引擎零依赖，pytest 是唯一的开发依赖 |
| **零依赖门禁** | `python scripts/check_zero_deps.py` | 见下方 |
| **静态 grep 门禁** | `grep -rnE '^(import\|from) baize\.ext' baize/*.py` | 核心模块不得顶层 import 扩展 |
| 测试 | `pytest tests/` | — |

**零依赖门禁为什么重写过？** 旧版是内联的 AST 代码，把**所有**非标准库 import 都判失败——包括那些被 `try/except ImportError` 包住的、放在函数体里的可选 import。结果是这个作业**从 V24（`7af42a5`）开始一直是红的，从来没有绿过一次**。

> **一个从来没人见过它变绿的门禁，等于一个所有人都学会忽略的门禁。**
>
> 新版把 import 分成两类：
> - **HARD**：模块级第三方 import → 会让 `import baize` 失败 → **判失败**
> - **SOFT**：`try/except ImportError` 包住 / 函数体内 / `TYPE_CHECKING` 里 → 包仍能 import，只是功能降级 → **列出来但不判失败**
>
> 现在它第一次通过了：
> ```
> ZERO-DEP CHECK PASSED: baize/ imports stdlib only at module level (5 optional import(s) allowed)
> ```

**静态 grep 门禁**用的是列 0 锚定（`^`），所以**缩进的 import 不算违规**——函数体内的 `from baize.ext import ...` 是被允许的例外。

### 3.2 `truth` —— 版本与测试数一致性

```bash
python scripts/sync_truth.py --check
```

失败长这样：

```
TRUTH CHECK FAILED - derived surfaces drifted from baize/__init__.py:

  README.md: tests badge advertises 650 cases, the suite collects 683

Run `python scripts/sync_truth.py` to regenerate them.
```

**这个门禁是有效的**——本次改造中新增了 22 个测试，它立刻发现 README 徽章还写着 650。

### 3.3 `install-smoke` —— 安装冒烟

验证"按文档安装真的能装上"。

### 3.4 `docker` —— 镜像构建与冒烟

```yaml
- name: Build image
  run: docker build -t baize:ci .
- name: Smoke test the image
  run: |
    docker run --rm baize:ci --version
    docker run --rm baize:ci doctor
```

**`docker run --rm baize:ci doctor` 必须通过。** 这条命令同时覆盖了 1.3（目录必须存在）和 1.1（技能库必须在）。

## 4. 本地跑一遍完整门禁

```bash
make gate
```

```
deps     →  python scripts/check_zero_deps.py
truth    →  python scripts/sync_truth.py --check
hygiene  →  python scripts/check_hygiene.py
cov      →  python scripts/coverage_gate.py
```

**顺序是刻意的：便宜的检查先跑。** 一个坏掉的承诺应该在几秒内失败，而不是等几分钟的覆盖率跑完才发现。

### 4.1 预期结果

```
ZERO-DEP CHECK PASSED: ... (5 optional import(s) allowed)
TRUTH CHECK PASSED: V37.0.0 Prometheus, 1334 tests collected, 9 count claims verified, no drift
HYGIENE GATE PASSED: 342 tracked files, none matching a banned pattern
COVERAGE GATE PASSED: 86.6% >= 85%
```

**四行都应该是 PASS。** 如果覆盖率那行报 `cannot verify`，说明覆盖率数据文件比源码还旧——先跑 `make cov`。门禁不会拿一份旧数据给出结论，也不会用旧数据凑一个绿色。低于 85% 时它报 `COVERAGE GATE FAILED`；正确做法是补测试，不是改小 `TEST_COVERAGE_THRESHOLD`（`tests/test_config.py` 有一条测试钉住这个值）。用例数与跟踪文件数每次提交都会变，`make gate` 打印的是当前树的值。

## 5. 生产部署清单

- [ ] 设置 `BAIZE_SERVE_HOST=0.0.0.0`（容器内必需）
- [ ] 配置模型端点（`BAIZE_MODEL_BASE_URL` / `BAIZE_MODEL_NAME` / `BAIZE_MODEL_API_KEY`）
- [ ] **用密钥管理注入 API key，不要写进镜像**
- [ ] 确认技能库在镜像里（`docker run --rm <img> python -m baize index build` 应输出非 0）
- [ ] 挂载持久化卷到 `BAIZE_PERSISTENCE_DIR`（否则容器重启会话就没了）
- [ ] 决定是否开启 `BAIZE_SANDBOX_ENABLED`（Linux 才有 Landlock）
- [ ] 决定是否开启 `BAIZE_ALLOW_FETCH_URL`（默认关闭）
- [ ] 决定是否开启 `BAIZE_MCP_ENABLED`（默认关闭）
- [ ] 接上 `/metrics` 到监控
- [ ] 用 `/health` 做存活探针
- [ ] 考虑 `BAIZE_LOG_FORMAT=json` 便于日志聚合
- [ ] 设定 `BAIZE_AUTONOMY_COST_CAP` 防止成本失控

### 5.1 关于"默认关闭"的三个开关

| 开关 | 默认 | 为什么默认关闭 |
| :--- | :--- | :--- |
| `BAIZE_ALLOW_FETCH_URL` | 关 | 网络访问是最大的数据外泄面 |
| `BAIZE_MCP_ENABLED` | 关 | 外部工具连接引入不可信输入 |
| `BAIZE_SANDBOX_ENABLED` | 关 | 平台差异大，开启可能影响兼容性 |

**"默认安全"比"默认方便"重要。** 需要时显式打开，并且清楚自己打开了什么。

## 6. 持久化

```bash
docker run -v /host/data:/app/persistence \
           -e BAIZE_PERSISTENCE_DIR=/app/persistence \
           -p 8787:8787 baize:ci
```

不挂卷的后果：容器一重启，**记忆、会话、技能索引、运行账本全部丢失**——等于每次都是全新的白泽。

需要持久化的内容：

```
persistence/     ← 记忆、会话、索引、账本、图谱
user_skills/     ← 自动蒸馏出的技能
projects/        ← Agent 生成的产出
```

## 本篇小结

- Dockerfile 里有**四个**必须理解的细节：`COPY assets/`（否则技能库为空）、不能 `COPY docs/`（会被 `.dockerignore` 过滤）、`mkdir projects`（否则 `doctor` 失败）、**ENV 名字必须真实存在**（否则静默绑定回环地址）。
- **ENV 名字写错是最阴险的**：三处看起来都对，就是不通，且无任何报错。
- 有一条测试专门防止 ENV 名字写错，且**被证明能抓到修复前的 Dockerfile**（6 条里失败 4 条）。
- CI 有四个作业：`test`（3×4 矩阵）、`truth`、`install-smoke`、`docker`。
- 零依赖门禁重写后**第一次变绿**——旧版从 V24 起一直是红的。
- `make gate` 的顺序是"便宜的检查先跑"，覆盖率 FAIL 是已知缺口。
- 生产部署要挂持久化卷，否则重启等于失忆。
