| 项目 | 实测值 | 复现命令 |

覆盖率下限为 85%。**是否达标以命令输出为准，不要在这里写死判决**——同一提交在工作树与全新克隆下会差 0.1 个百分点（被 gitignore 的 `.env` 是否存在，会影响 `serve.py` 与 `cli.py` 的 6 行），写死一个数就必然在其中一处是错的。

### 四条设计原则

- **白盒**：纯标准库，审计面小到可以通读
- **可信**：NO FAKE DONE —— 没验证过的成功不许上报
- **可控**：工作区约束 + deny-list + 可选 OS 沙箱
- **可复现**：会话是追加写 JSONL，可回放、可续跑

## 关于本系列的两个诚实声明

**第一，这些教程里的输出是真的。**

每一段"真实输出"都是在本机执行后粘贴的。包括：

- `baize run` 的完整运行输出（用一个脚本化的 OpenAI 兼容桩服务产生，引擎走的是真实代码路径）；
- `baize team` 的失败输出（Verifier 正确拒绝了一次不匹配目标的产出）；
- `baize doctor` / `baize gate` / `baize bench` 的原始输出。

**第二，有些东西是"红"的，教程不会帮你藏起来。**

- 覆盖率曾经是 77.4% < 85%，`make gate` 最后一项 FAIL；那 24 个被漏掉的文件提交后是 86.6%，
  门禁转绿。当前数字不写在这里——`make cov` 会打印它；
- 上面「测试与覆盖率」那节曾经写着一句「当前**未达标（门禁 RED）**」，而那是错的：门禁在 86.6% 时
  就已经转绿。这句话被漏在门禁之外——`sync_truth.py` 钉住了本表里的每一个计数，唯独没有钉判决。
  删掉过期的数字却留下过期的判决，比两者都留着更容易骗人：判决才是读者会记住的那一半，
  而一个只读到那一节的读者，看到的只有「不达标」；
- 有 3 个测试是跳过的（环境能力不足，不是被忽略的失败）；
- 部分能力在 Windows 上会降级（OS 沙箱只有逻辑层）。

**把这些写出来，比假装一切正常有用得多。**
