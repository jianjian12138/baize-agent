# 第 3 篇：跑通你的第一个任务 —— run / team / bench 实战

> 适用读者：环境已配好（第 2 篇），想真正看到白泽干活的小白。本篇带你跑通三种运行模式，并读懂屏幕上的输出。

---

## 3.1 先认识三种"运行模式"

白泽有几种不同的"干活方式"：

| 命令 | 模式 | 适合场景 |
|------|------|---------|
| `python -m baize run "目标"` | **单 Agent**：一个智能体自己规划+执行 | 单一、明确的任务（写个函数、补测试） |
| `python -m baize team "目标"` | **多 Agent 团队**：规划者+执行者+验收者分工 | 复杂、需要质量保证的任务（做一个接口并验证） |
| `python -m baize bench` | **基准自检**：跑一组确定性性能测试 | 验证引擎本身正常（不需要模型） |

---

## 3.2 模式一：单 Agent 跑起来

### 最简跑法

```bash
python -m baize run "为 utils.py 写 3 个单元测试"
```

白泽会：
1. 读取你的目标；
2. 进入"反思规划"——把目标拆成子步骤；
3. 在沙箱里调用工具（读文件、写测试、跑 pytest）；
4. 每过几步"自我反思"一次，看是否走偏；
5. 输出最终结论。

### 读懂屏幕上的 TUI 进度

运行时会看到类似这样的实时进度（TUI = 终端界面进度条）：

```
session: a1b2c3d4
  ▸ stage: plan       reflect: 把目标拆成 3 个子任务
  ▸ stage: act         tool: read_file  utils.py
  ▸ stage: act         tool: write_file tests/test_utils.py
  ▸ stage: observe     pytest 3 passed
  ▸ stage: reflect     进度良好，无需调整
  ...
────────────────────────────────────────────────────────
最终结论：已为 utils.py 生成 3 个单元测试，全部通过。
verdict: PASS (steps=8, tool_calls=5, session=a1b2c3d4)
```

> 这些 `[stage]`、`tool:`、`reflect:` 行是**真实发生的事件**，不是装饰。每一行对应引擎内部的一个动作。

### 两个常用开关

```bash
# 不加颜色（适合把日志存文件 / 老式终端）
python -m baize run "目标" --no-color

# 只看总结，不看逐步过程
python -m baize run "目标" --quiet
```

### 断点续跑

每次运行都有一个 `session` id。如果中断了，可以接着跑：

```bash
python -m baize run "继续上次任务" --resume a1b2c3d4
```

因为会话记成了 JSONL，**状态不丢**（见第 4 篇）。

## 3.3 模式二：多 Agent 团队

当你想要"更靠谱"的结果，用 team 模式：

```bash
python -m baize team "实现用户登录接口并端到端验证"
```

内部会启动三个角色：

```
Director（规划者）  → 把目标拆成可验证的子任务清单
   ↓
Executor（执行者）  → 逐个子任务写代码、调工具
   ↓
Verifier（验收者） → 独立核验每个子任务是否真的达成
   ↓ (未达成则注入问题，Executor 重试)
```

屏幕上会看到每个子任务的验收结果：

```
==============================================================
[1/3] PASS  #1 实现 POST /login 接口
[2/3] PASS  #2 实现 JWT 生成与校验
[3/3] FAIL  #3 端到端测试 (retried)   issue: 测试未覆盖过期 token
==============================================================
overall: FAILED (3 sessions)
```

> 注意：Verifier 是**独立、严格**的。它会用工具自己去验证（比如真的跑测试），而不是听 Executor "口头说完成了"。这就是 **NO FAKE DONE** 原则的体现。

---

## 3.4 模式三：基准自检（不需要模型）

`bench` 完全不依赖模型，用来确认引擎本体没坏：

```bash
python -m baize bench
```

输出 `4/4 benchmarks passed` 即正常（vector / rag / memory / graph 四项）。

---

## 3.5 没配模型会怎样（fail-closed 行为）

这是白泽"防御式设计"的一个体现。如果你**没配模型**就跑 `run` / `team`：

```bash
$ python -m baize run "写个函数"
model endpoint not configured - set BAIZE_MODEL_BASE_URL / BAIZE_MODEL_NAME (and API key) in .env
```

并且**退出码是 2**（不是 0，也不是崩栈）。这意味着：
- 它**明确拒绝**在没有"大脑"的情况下瞎跑；
- 自动化脚本能根据退出码判断"这次没配好"，而不是误以为"跑完了"。

> 这种"宁可明确报错，也不假装能干活"的设计，是白泽可信的关键。

## 3.6 构建并使用技能索引

白泽有一套"方法论技能"（怎么调研、怎么写代码等）。先构建索引：

```bash
python -m baize index build
# 输出：indexed 249 skills from 4 source(s)

python -m baize index search tdd
# 输出：匹配到的与"测试驱动开发"相关的技能
```

构建后，Agent 在运行时能**按需检索**这些技能（渐进式披露），用到的才加载。

---

## 3.7 用 Web 仪表盘"看着它跑"

除了命令行，还能开一个网页仪表盘实时看进度（详见第 8 篇）：

```bash
python -m baize serve --port 8787
```

浏览器打开 `http://127.0.0.1:8787` 即可看到运行面板。

---

## 3.8 第一次跑的完整示例

把前三步串起来，一次成功的"首跑"长这样：

```bash
# 1) 确认环境
python -m baize doctor          # 看到 PASSED

# 2) 构建技能索引（可选，但推荐）
python -m baize index build

# 3) 让单 Agent 干活
python -m baize run "在 baize/ 里找一个最可能被误用的函数，写注释说明风险"

# 4) 想更严谨？换成团队模式
python -m baize team "为上面的风险点补一个回归测试"
```

---

## 3.9 本篇小结

- 三种模式：`run`（单 Agent）、`team`（多 Agent 团队）、`bench`（自检）。
- TUI 进度里的每一行都是**真实事件**，可审计。
- 没配模型时 `run`/`team` 会**退出码 2 明确拒绝**，不会假装能跑。
- `--resume <session_id>` 可断点续跑，因为会话是 JSONL 持久化的。
- `team` 模式的 Verifier 会**独立用工具验证**，防止"假完成"。
