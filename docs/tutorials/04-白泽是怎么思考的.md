# 04 · 白泽是怎么"思考"的

> 目标：理解 `baize run` 内部那个循环。读完你应该能回答：
> 它为什么不会无限循环？上下文满了怎么办？什么时候会停下来反思？

---

## 1. 主循环：思考 → 行动 → 观察

`baize/agent.py` 里最核心的六行：

```python
for step in range(1, self.max_steps + 1):
    # 1. 上下文太长？先压缩
    if _total_chars(self.session.messages) > self.compress_chars:
        n = compress_context(self.session.messages)

    # 2. 问模型：下一步做什么
    # 3. 模型说"调用工具" → 执行工具，把结果塞回上下文 → 回到第 1 步
    # 4. 模型说"我说完了" → 结束，outcome = final
```

对应到你在第 03 篇看到的输出：

```
   0.0s -> tool     write_file(...)      ← 第 1 轮：模型决定写文件
   0.0s -> tool     read_file(...)       ← 第 2 轮：模型决定读回来验证
Done. I created ...                      ← 第 3 轮：模型给出最终答复
```

`steps=3` 就是这么数出来的。

## 2. 四个"刹车"（它为什么不会失控）

一个能自己调工具的 Agent，最大的风险是**停不下来**。白泽有四道独立的刹车：

### 2.1 步数上限

```bash
BAIZE_AGENT_MAX_STEPS=24
```

硬上限。到顶就停，`outcome: max_steps`。

### 2.2 死循环检测

```bash
BAIZE_LOOP_DETECT_WINDOW=3
```

引擎给每次工具调用算一个签名：

```python
sig = f"{name}:{json.dumps(args, sort_keys=True, ensure_ascii=False)}"
```

**名字 + 排序后的参数**。如果同一个签名连续出现 `loop_window × 2 = 6` 次，直接中止：

```
[loop_detected] bash repeated 6 times - aborting
outcome: loop_detected
```

> 为什么要检测？因为模型最常见的失败模式就是**用同样的参数反复重试同一个失败的操作**。人类工程师会换方法，模型不会——除非你逼它。

### 2.3 成本上限

```bash
BAIZE_AUTONOMY=balanced
BAIZE_AUTONOMY_COST_CAP=200000
```

自主度策略（`L1`~`L3` 语义）带一个 token 成本上限。`balanced` 是默认档。

### 2.4 质量门

```bash
BAIZE_QUALITY_THRESHOLD=0.8
```

产出低于这个质量分不会被视为完成。

## 3. 反思检查点：让它自己发现问题

```bash
BAIZE_REFLECT_EVERY=6
```

每 6 步，引擎会往上下文里插一段**强制的自我评估提示**（`agent.py:50`）：

```
REFLECTION CHECKPOINT - pause and self-assess before continuing:
1) Am I measurably closer to the goal than N steps ago?
2) Have any actions failed repeatedly? If so, change strategy - do NOT retry the same thing.
3) What is the single most valuable next action?
Answer in 2-3 short lines, then continue working (or give the final answer if done).
```

这三个问题设计得很讲究：

| 问题 | 防的是什么 |
| :--- | :--- |
| 我比 N 步前更接近目标了吗？ | **原地打转** |
| 有操作反复失败吗？ | **无效重试** |
| 下一步最有价值的事是什么？ | **没有优先级地乱试** |

第 2 问尤其关键——它明确写着 `do NOT retry the same thing`，和 2.2 的死循环检测形成"软提醒 + 硬刹车"的组合。

## 4. 长程任务：上下文压缩

```bash
BAIZE_CONTEXT_COMPRESS_CHARS=60000
```

每轮开始前检查上下文总字符数。超过 6 万就调用 `compress_context()`：

```python
n = compress_context(self.session.messages)
if n:
    obs.inc("context_compressions")
    self.hooks.pre_compact(n)
    self._emit("compress", f"compressed {n} old observations")
    self.session.append({"compressed": n}, kind="compress")
```

你在终端会看到：

```
   0.0s .. compress compressed 12 old observations
```

**三个设计细节：**

1. **只压缩"旧的观察"，不动用户目标和最近的对话**——否则模型会忘记自己在干什么。
2. **压缩本身是一条会话记录**（`{"compressed": n}`）。所以事后复盘时你知道第几步被压过，信息不是凭空消失的。
3. **有钩子**（`hooks.pre_compact`），你可以在压缩前把原始内容存到别处。

## 5. 让它先想再动手

系统提示里有一段结构化思维链指令（`COT_SYSTEM_INSTRUCTION`）：

```
When facing complex tasks, multi-step decisions, or ambiguous situations,
ALWAYS begin your response with a <thinking>...</thinking> block that outlines
your reasoning step-by-step before proceeding with tool calls or a final answer.
For trivial single-step responses you may skip the thinking block.
```

注意最后一句：**简单任务允许跳过**。这是刻意的——强制所有请求都长篇大论地"思考"，只会浪费 token 和延迟。

---

## 6. 四个"停止原因"（`outcome`）

`AgentResult` 里的 `stopped_reason` 只有四个合法值：

| `outcome` | 含义 | 你该做什么 |
| :--- | :--- | :--- |
| **`final`** | 模型认为完成了 | 检查产出物 |
| **`max_steps`** | 撞上 24 步上限 | 任务太大，拆小；或调大 `BAIZE_AGENT_MAX_STEPS` |
| **`loop_detected`** | 同一操作重复 6 次 | 模型卡住了。看会话记录，找出它在重复什么、为什么 |
| **`error`** | 异常（模型连不上、工具崩了） | 看 `stderr` 里的真实异常 |

**只要不是 `final`，这次运行就没有完成任务。** 不要看到进程退出码是 0 就以为成功了。

## 7. 自主度与模式

除了标量滑块，白泽还有**具名模式**（`BAIZE_MODE`）：

```bash
BAIZE_MODE=''            # 默认
BAIZE_PLAN_MODE=0        # 计划模式：先出计划再执行
```

模式携带的权限**优先于**标量滑块——这是 `resolve_mode()` 的规则，避免"设了模式但某个滑块偷偷放权"。

想体验计划模式：

```bash
BAIZE_PLAN_MODE=1 python -m baize run "..."
```

在计划模式下，写操作类工具会被拦下，只允许只读操作——先让模型把计划说清楚。

## 8. 相关配置速查

| 配置键 | 默认值 | 作用 |
| :--- | :--- | :--- |
| `BAIZE_AGENT_MAX_STEPS` | `24` | 单次运行的步数上限 |
| `BAIZE_REFLECT_EVERY` | `6` | 每多少步插入一次反思检查点 |
| `BAIZE_LOOP_DETECT_WINDOW` | `3` | 死循环检测窗口（×2 = 触发阈值） |
| `BAIZE_CONTEXT_COMPRESS_CHARS` | `60000` | 上下文压缩阈值（字符） |
| `BAIZE_AUTONOMY` | `balanced` | 自主度档位 |
| `BAIZE_AUTONOMY_COST_CAP` | `200000` | token 成本上限 |
| `BAIZE_QUALITY_THRESHOLD` | `0.8` | 质量门限 |
| `BAIZE_PLAN_MODE` | `0` | 计划模式开关 |
| `BAIZE_LLM_MAX_RETRIES` | `2` | 模型调用重试次数 |
| `BAIZE_RATE_LIMIT_RPM` | `60` | 每分钟请求上限 |
| `BAIZE_RATE_LIMIT_TPM` | `60000` | 每分钟 token 上限 |

## 9. 实验：亲手触发一次死循环

把第 03 篇的桩服务改成**永远返回同一个工具调用**：

```python
SCRIPT = [
    {"content": "trying again...",
     "tool_calls": [_call("c1", "bash", {"command": "exit 1"})]},
]
```

然后跑 `baize run "随便什么目标"`。你会看到：

1. 前几步正常执行；
2. 到第 6 次相同调用时，引擎打印 `loop_detected` 并中止；
3. `outcome: loop_detected`。

**这就是"硬刹车"生效的样子。** 对比一下：没有这个机制，它会烧掉你所有的 token。

---

## 本篇小结

- 主循环 = 压缩上下文 → 问模型 → 执行工具 → 循环。
- 四道刹车：**步数上限 / 死循环检测 / 成本上限 / 质量门**。
- 每 6 步插入一次**反思检查点**，逼模型自问"我离目标更近了吗"。
- 上下文超过 6 万字符会**自动压缩旧观察**，且压缩本身有记录。
- `outcome` 只有四个值，**只有 `final` 代表成功**。
- 具名模式（如计划模式）的权限**优先于**标量滑块。
